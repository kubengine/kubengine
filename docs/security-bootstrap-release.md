# SSH 首次纳管与发布配置

AsyncSSH 管理接口与 pyinfra 部署均严格验证主机身份。未知或变化的主机密钥会阻止连接，密码认证和
`--skip-verify` 都不会关闭这项检查。

首次纳管时，通过节点控制台等可信渠道取得 SSH 主机公钥及指纹并核对。
将确认的公钥按 OpenSSH known_hosts 格式保存到执行端 `~/.ssh/known_hosts`，
或通过 `kubengine cluster config --known-hosts /path/to/verified_known_hosts`
显式指定引导文件。单独运行 `ssh-keyscan` 只能获取网络对端宣称的公钥，
不能证明主机身份。后续命令使用执行端默认 known_hosts，因此应保留这些
已核验条目。

pyinfra 的部署 inventory 也固定要求严格验证，不能通过公共参数或分组参数
关闭验证，也不会继承本机 SSH 配置中关闭身份校验的设置。

互信配置保留既有 authorized_keys，并在锁内原子合并新公钥。节点之间的
known_hosts 条目来自已通过身份验证的连接，不再重新扫描并删除旧记录。
遇到已有记录冲突时停止更新；节点重装等合法密钥变化也需要通过可信渠道
核实后显式更新。工具不会自动撤销既有密钥授权。

RPM 源码归档只能从已经提交、源码无修改的 Git 工作区构建。归档读取提交
中的普通文件白名单，忽略未跟踪文件，并排除运行配置、证书私钥、token、
数据库和部署状态；不跟随符号链接。`config/application.example.yaml`
是唯一发布的应用配置模板，RPM 将其以 0600 权限安装为 application.yaml，
且保留已有安装的配置。发布前需提交经审核的源码和模板；新增源码未提交时
不会进入归档。不要把安装凭据填写进发布模板。

已有 Kubernetes 控制面且部署状态缺失或配置变化时，`deploy` 在生成证书和
执行基础设施变更前拒绝自动重新 bootstrap。相同配置的失败续跑仍然保留；
节点侧 kubeadm 操作用锁防止并发重入，已有配置须通过只读 API 检查才跳过
init/join。部分初始化状态、权限不足和 API 故障均要求先排查，不会被解释为
可以重新初始化的空节点。新增 Worker 继续使用 `scale`；这项保护不代替完整的
配置更新、升级或灾难恢复流程。

RPM 安装脚本现在会明确报告依赖安装及初始化失败，并使用实际数据库路径与
正确的应用子命令。当前依赖仍通过 pip 获取；完全离线、锁定依赖的安装制品
需要后续单独建设，本次没有下载或安装依赖。

应用卸载会先检查 Helm release，再持久化 `cleaning` 状态并等待资源删除完成。
只有明确卸载成功才删除管理记录。Helm 的卸载等待超时后可能已清除 release
历史，因此曾经开始部署或清理的应用即使查不到 release，也不能据此确认资源
已经消失；包括 `healthy`、`unhealthy`、`cleaning`、`anomaly` 在内的这些记录
会被保留，并明确要求人工核实残留工作负载、终结器及存储资源。Helm 仍返回
`uninstalled` 历史时也同样保留记录，避免重试时只清除历史却遗漏实际资源。
仅从未开始部署的 `pending` 记录在成功查询且 release 不存在时可直接移除。
这意味着进程在卸载成功后、删除数据库记录前退出时，也可能需要人工核对。

Pod 健康检查遇到空列表会继续等待，最终仍为空则报告无法确认健康。
成功完成且仍存在的 Job Pod 可通过检查；不创建 Pod 或 Job Pod 已被清理的
Chart 需要相应资源类型的健康检查，本检查器不会把空列表判为应用正常。
