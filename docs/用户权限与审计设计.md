# 用户、权限与操作审计设计

## 实施状态与边界

2026-11-19：数据库身份、统一资源授权、敏感操作授权、任务撤权复核、操作审计及
管理页面已实现。入口见[接口与任务授权清单](接口与任务授权清单.md)，使用和运维
步骤见[使用指南](用户权限与操作审计使用指南.md)。`/me` 返回 `authorization_stage: rbac`，
三类角色按以下矩阵执行，管理员业务入口默认拒绝普通用户。

平台用户 RBAC 与 Kubernetes 连接身份的 RBAC 是两层约束。平台管理员也受连接身份
的权限上限约束。共享 SDK 连接不具备 Kubernetes 用户模拟或强多租户隔离；拥有工作负载
写权限的用户可能通过挂载 Secret、使用 ServiceAccount 或 exec 读取业务凭据。

## 最终权限矩阵

角色 ID 固定为 `platform_admin`、`namespace_operator`、`readonly`，用户名不可重命名，
用户 ID 为稳定的 UUID hex。每名用户一个内置角色；命名空间绑定是显式名称集合，
不支持通配符、`_all`、`_cluster` 或用户自定义角色。

| 动作/权限点 | 平台管理员 | 命名空间运维 | 只读用户 | 范围 | 审计事件 |
| --- | --- | --- | --- | --- | --- |
| profile.read / password.change / session.logout | 允许 | 允许 | 允许 | 本人 | identity.password.change / session.logout |
| users.manage（创建/启停/角色/范围/敏感授权/重置密码） | 允许 | 拒绝 | 拒绝 | 平台 | identity.user.create/update/password.reset |
| audit.read | 允许 | 拒绝 | 拒绝 | 平台 | audit.query（不记录查询敏感正文） |
| resource.read（含状态、关联 Pod、事件、日志） | 允许 | 允许 | 允许 | 普通用户仅绑定 namespace | resource.read；敏感访问/拒绝必须记录 |
| resource.create / resource.update | 允许 | 允许 | 拒绝 | 普通用户仅绑定 namespace 的明确允许类型 | resource.create/apply |
| secret.read | 允许 | 独立授予 | 独立授予 | 在角色 namespace 范围内取交集 | secret.read |

| pod.files.write | 允许 | 独立授予 | 独立授予 | 在角色 namespace 范围内取交集 | pod.file.upload/mkdir/rename/delete |
| resource.history / resource.preview | 允许 | 依读取/写入权限 | 只读历史，不允许修改预览 | 资源范围 + Secret 明文策略 | resource.history/preview |

| app.manage（配置、Helm 部署、重试、删除、详情） | 允许 | 拒绝 | 拒绝 | 平台及其托管 namespace | app.* |
| artifact.manage（仓库查询、标签、上传、删除、导入、清理） | 允许 | 拒绝 | 拒绝 | 平台 | artifact.* / image.* |
| infra.manage（SSH、基础设施命令、文件、集群编排） | 允许 | 拒绝 | 拒绝 | 平台 | infra.* |
| platform.notifications / 模拟后台任务 | 允许 | 拒绝 | 拒绝 | 平台 | task.create/execute |

管理员的上述权限为内置角色权限，无需再显式勾选四项敏感授权。普通用户的敏感授权
仅是额外动作能力，不能扩大 namespace 范围；例如只读用户可以被显式授予终端，
这属于高风险例外，不能再把该账号解释为不具备容器写能力的只读身份。

普通 namespace 资源使用明确的 GVK/资源类型允许清单（Pod、Deployment、StatefulSet、
DaemonSet、ReplicaSet、Job、CronJob、Service、Endpoints、Ingress、NetworkPolicy、
ConfigMap、Secret、PVC），新类型及自定义资源默认拒绝，不能仅依赖 discovery 的
`namespaced=true` 决定允许。普通用户写 Secret 还需 `secret.read`，以保证预览、
差异和写入结果不会形成无明文授权的旁路。API 别名统一映射后再判断类型和范围。

## 返回边界与执行顺序

- 列表、计数、搜索、namespace 选项、关联资源、监控与日志都使用同一授权集合。
  跨 namespace 查询应分别查询获授权集合并合并，过滤后再计算总数和分页；不得返回
  未授权名称、总数或 namespace 存在性。集群级类型不接受伪造的 namespace 来降级。
- Secret 元数据只允许名称、namespace、UID、resourceVersion、创建时间、类型与键名；
  `data`、`stringData`、annotations 及可能包含值的其他字段统一隐藏。没有 `secret.read`
  时，不得从详情、YAML、编辑预览、差异、历史快照、创建预检或错误信息返回值。
  `reveal_secret=true` 是显示意图，不是权限凭据。
- 日志是 namespace 内普通读取；文件目录、下载及内容读取统一需要 `pod.files.read`。
  上传、新建、删除、重命名（含源与目标路径）需要 `pod.files.write`。
  终端需要 `pod.terminal`，不自动授予文件 API 权限。
- 普通用户 YAML 创建在解析并规范化全部文档、识别 GVK 和真实 scope 后，逐项检查
  namespace、允许类型和敏感权限；存在一项拒绝就整批 403，在任何集群写入前结束。
  预检、create、apply 都重新鉴权，预检令牌不缓存权限，也不能代替审计预写。
- 身份有效但动作/范围不足返回 403，前端保持登录并刷新 `/me`；身份停用、凭据变更、
  会话失效返回 401。数据库不可用返回 503，不能回退配置认证。

## 数据模型与会话一致性

身份基础已实现的表：

| 表 | 关键字段及约束 |
| --- | --- |
| console_user | user_id 主键；username 唯一且不可修改；password_hash；enabled；role；auth_revision；revision；created_at/updated_at（UTC Unix 秒） |
| identity_role | 固定角色 ID 与中文名称；不提供角色编辑接口 |
| identity_namespace | (user_id, namespace) 复合主键 |
| identity_sensitive_grant | (user_id, permission) 复合主键；仅允许四个敏感权限 |
| identity_migration | 迁移名称主键与完成时间；identity-v1 完成标记 |
| auth_session（沿用） | sid、username、凭据版本、到期与撤销时间 |
| revoked_token（沿用） | token SHA-256 与到期时间，不存明文 Token |

JWT 包含稳定 `uid`、用户名、`sid`、凭据版本和到期时间，角色/namespace/敏感授权
每次从数据库加载，JWT 内不缓存授权。凭据版本绑定 user_id、auth_revision 和旧凭据
哈希；数据库迁移后的旧版令牌需要重新登录。配置用户原有 bcrypt 哈希保持原样。

停用、重新启用和密码变更递增 auth_revision，并在同一事务撤销该用户全部 sid。
因此重新启用不能恢复旧令牌，自己改密和管理员重置密码也都要求重新登录。
单纯角色/namespace/敏感授权变化不撤销登录，在下一次请求按新权限判断并返回 403。
更新请求必须携带上次读取的 revision；过期版本返回 409，避免覆盖他人修改。

所有用户管理写入使用 SQLite `BEGIN IMMEDIATE`，在数据库写锁内重新检查操作者
是否仍为启用管理员，再校验并修改目标用户。最后一个启用管理员不能被停用或降权。
不提供用户删除接口，避免用户名复用、历史身份断链及删除绕过保护；停用用于退役。
用户管理查询显式列出公开字段，不返回密码哈希、旧 SK 哈希、凭据版本。

终端和普通 WebSocket 目标复核周期 30 秒，且输入/广播/响应前重新校验；身份失效或
敏感授权撤回时断开。已接入命名空间与敏感动作复核；Pod 终端周期为 15 秒，平台通知连接为 30 秒。

## 后台任务与审计的后续接入设计

以下为本版实现约定；具体存储采用 task/image_import_task 的 auth_context JSON 与审计关联字段：

1. task、image_import_task、批次增加 actor_id、request_id、audit_id 与动作/范围授权
   上下文；已有 YAML revision 保留 actor 展示名，并关联稳定 actor_id、batch_id。
   HTTP 创建记录时从认证对象填充，不能信任请求体中的 actor。
2. worker 在领取任务后、每个新的受限步骤开始前重新读取身份并授权。停用/撤权后
   不再发起新外部操作，任务标记 authorization_revoked；已生效步骤不自动反向撤销，
   保留部分完成事实和资源标识，由管理员按幂等恢复流程处理。必要清理由明确的系统
   维护身份执行，仅限已记录的任务临时资源，并单独审计，不能借清理继续部署。
3. 旧任务缺少发起者时不能默认冒充 admin。迁移前先盘点和排空；遗留任务暂停等待
   管理员接管，记录接管审计后才执行。CLI/系统调度使用明确 service_actor。
4. audit_event 为应用层追加记录：event_id、UTC 时间、actor_id、操作者快照、动作、
   资源类型/name/namespace、直接连接来源地址、request_id、batch_id/task_id/revision_id、
   结果、错误分类。不保存完整请求体、密码、JWT、Secret 值、文件内容、终端输入或输出。
   代理来源只有在配置可信代理链时才采用，不直接信任客户端 X-Forwarded-For。
5. 身份/授权/写入/敏感读取和拒绝均可追踪；写入前必须成功建立 pending 审计，否则
   503 且不执行。外部写入生效但审计收尾失败返回“结果待核实”及请求编号，禁止提示
   直接重试；数据库内身份变更与其审计尽量在同一事务提交。
6. 仅管理员查询审计；支持用户、时间、动作、namespace、资源、结果及分页。无普通
   用户编辑/删除接口。默认保留窗口 90 天，管理员通过 audit-archive 命令归档到本机受限目录后可显式清理，
   归档包含时间范围、校验摘要并校验恢复。不自动删除 pending 事件，命令与配置见使用指南。
   应用层追加记录不防御数据库管理员篡改，不能宣称具备防篡改审计能力。

## Kubernetes 最小权限与准入前提

共享后端连接建议使用专用 ServiceAccount；分别参考现有 SDK、YAML 创建/编辑、Pod
操作 RBAC 示例，按实际启用功能裁剪，禁止直接把示例作为完整生产权限自动套用。
基础设施与 Helm 所需的更高权限仍由管理员在既有连接中显式配置。

允许 namespace 运维写工作负载前，管理员必须评估并配置 Pod 安全准入、禁止特权/
宿主机 namespace/hostPath、允许的镜像来源、可使用的 ServiceAccount 与挂载 Secret
范围、默认 ServiceAccount Token 挂载策略、网络策略及资源配额。不能仅靠禁止
RoleBinding 或隐藏 Secret 按钮声称完成隔离。应用不自动更改客户集群准入策略。
如果共享连接身份下不能落实这些约束，应保持普通用户写入/终端能力关闭；需要强隔离
时采用独立集群/连接身份或后续 Kubernetes 用户模拟方案。

## 身份迁移、备份与回滚

1. 核对实际 KUBEENGINE_CONFIG、root_dir、当前服务版本、配置用户以及两个服务进程。
   发布前停止 API/worker 或使用 SQLite backup API 建立一致备份，不直接复制活动中的
   WAL 主文件；备份 `${root_dir}/config/sqlite.db`、实际配置、jwt-signing.key 及 YAML
   历史加密密钥，使用私有目录和 0600 权限，记录文件摘要与版本。备份不可进入 Git。
2. 服务启动在 SQLite 写锁内建身份表、种下三个角色，再一次性导入全部配置用户为
   管理员并写入 identity-v1 完成标记。任一插入失败整批回滚，可修正来源后重新启动。
   并发执行仅第一个进程导入；完成标记存在时完全不读取配置用户，不增补、不覆盖。
3. 配置从此只承担初始引导；创建/停用/角色/授权/改密都以数据库为准。保留配置中的
   旧用户名或密码哈希不会恢复停用账号。丢失数据库必须按备份恢复，不能清空数据库
   作为普通修复手段，否则会失去用户状态并重新导入旧管理员。
4. `kubengine app set-password` 只修改数据库中已有、启用、角色为管理员的 admin。
   该命令可在首次启动前完成幂等迁移；不修改旧配置、不重新启用停用账号。其他用户
   的管理员重置通过管理 API 完成。新密码至少 12 字符且 UTF-8 不超过 72 字节。
5. 测试环境恢复验证应先停止所有写入者，恢复数据库、相应密钥与配置到隔离 root_dir，
   重跑幂等迁移，核验用户 ID、停用状态与授权保持、旧哈希登录可用、停用登录拒绝、
   新旧密码和退出行为符合预期。自动测试覆盖迁移失败回滚/重试、幂等及备份恢复；
   目标环境的数据库快照也已完成迁移、原身份保留和真实 Kubernetes 范围查询预演，
   发布验证和备份位置见正式部署记录。
6. 回滚前必须先限制普通用户流量并停止 worker；旧版忽略新授权，并且会重新信任
   配置用户。只有恢复与旧版相匹配的受限管理员配置、数据库和密钥，并确认普通账号
   无法进入旧接口后才能开放。不要在带普通用户流量的环境直接切回旧版。

发布前后验证与备份信息记录在正式部署记录中；本文件保留长期设计依据。
