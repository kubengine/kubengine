# 统一任务恢复与部署幂等

本轮在已有安全修复之上，统一应用任务与镜像任务的租约、续租和执行所有权校验，并补齐应用提交幂等和 CLI 部署检查点。前端 `/opt/dashboard` 同步接入部署幂等键。保留原有任务表及状态枚举，避免破坏既有 API。

## 应用与镜像任务

应用部署、删除继续与资源记录同事务提交，由独立 worker 持续领取。共享 `TaskLease(owner, attempt)`、续租循环和数据库条件更新：只有仍处于运行态、owner/attempt 相符且租约未过期的执行者可以写入进度或终态。失败的业务任务等待显式重试；运行中断且租约到期的任务自动恢复。镜像资源清理失败仍按已有维护机制后台重试。

应用任务还绑定资源 UUID、Helm release 名称和 `operation_version`。新的清理请求会递增版本，使旧部署停止后续命令及资源状态写入。每个任务与资源仍使用本机文件锁串行化外部操作；租约到期不会允许另一执行者绕过尚未释放的资源锁。

应用执行逻辑位于 `core/services/app_deployment.py`。恢复部署时先查询 Helm；已部署的 release 必须匹配任务的 Chart、版本和自定义 values，并重新通过健康检查。名称相同但配置不同、处于未完成状态或查询失败时，保留资源与管理记录并报告失败。

清理成功后先保存 `cleanup_confirmed`，再删除资源记录。若记录删除失败或进程中断，重试复用原任务、阶段和递增的 attempt，在确认 release 仍不存在后完成记录删除。如果卸载后、检查点写入前进程退出，现有记录仍被保留：单凭 release 不存在不能证明所有 Kubernetes 资源已经删除，需要人工核对。

## 提交与重试协议

`POST /api/v1/app/deploy` 接受可选的 `Idempotency-Key` 请求头，字符限定为字母、数字及 `._:-`，长度 1–128。键按登录用户名和部署操作隔离。

| 请求 | 结果 |
| --- | --- |
| 同一用户、同一键、相同参数 | 返回原应用的当前状态，不新增资源或任务 |
| 同一键、不同参数 | HTTP 409 |
| 原应用已删除或其身份已变化 | HTTP 410，不重新创建 |
| 未提供键 | 兼容旧客户端，每次提交视为新的部署 |

参数摘要覆盖名称、应用模板 ID、Chart、版本和提交配置。幂等记录与资源、任务在同一个数据库事务内写入；记录只保存摘要和资源引用，不保存额外的配置明文。目前幂等记录保留为删除后的防重放凭据，不自动过期。

失败部署可调用 `POST /api/v1/app/cluster/{cluster_id}/retry`。同一资源当前意图的待执行/执行中任务会复用；失败任务重新入队并保留阶段。已有清理请求、正在清理或清理异常的应用拒绝部署重试。清理失败继续调用原 DELETE 接口重试。

前端同一登录会话、同一份未确认成功的表单复用随机请求键，保存在 sessionStorage 中，网络错误后重试或刷新页面后再次提交仍可使用原键。存储内容仅包含摘要和随机键，不保存表单内容。浏览器禁用存储时退回当前页面内复用。服务端确认成功后清除待确认键，后续新部署可使用新键；表单等待请求结束再解除加载状态。

## CLI 检查点与组件重试

- `deploy`、`scale`、`reset-state` 共用安装目录内的互斥锁，阻止同时修改节点、共享制品和部署状态。
- `.k8s_deployment_state.json` 升级为版本 2，保留原字段；每步记录 owner、attempt、阶段及输入摘要。结果与摘要一并写入 0600 临时文件，经 fsync 和原子替换提交。损坏或不受支持的状态明确报错，不视作首次部署。
- 每个组件对脚本、共享 helper、执行包装器、SSH/配置代码、部署参数以及声明的模板、Chart、离线包计算 SHA-256。仅在该组件成功且输入未变化时跳过；执行中输入变化会拒绝成功检查点。渲染输出不参与摘要，模板源参与摘要。新增组件或外部输入时，需更新 `core/deployment_inputs.py` 的依赖清单。
- 八个 Helm 组件采用 `upgrade --install --wait --timeout 5m`，重试可复用已有 release；MetalLB 与 ingress-nginx 的 Chart 路径改为实际 `deploy_src`。
- 扩容将已加入但未写回配置的请求节点补写到实际加载的配置文件。持久化失败会报错，可再次执行相同 scale 请求补齐。

检查点用于相同部署意图的续跑，不是持续资源巡检：组件完成后发生的外部漂移不会仅凭摘要被检测出来。已有控制面的配置变更保护继续生效；扩容改变 Worker 配置后，不能将旧 deploy 检查点视为新拓扑的完成证明，后续 deploy 仍需匹配的配置/检查点或单独规划更新。不要删除状态文件来绕过初始化保护。

## 升级与运行

1. 停止旧 API 和 worker，确认旧进程退出后一起更新后端。启动时自动补齐应用租约、阶段和资源版本字段，以及部署幂等记录表。不要混跑新旧执行器。
2. 已绑定资源 UUID 和 Helm 名称且身份仍相符的任务按任务顺序补齐操作版本。仅有数字 ID、身份不符或操作含糊的旧任务继续拒绝自动执行，不为其猜测资源身份。
3. 统一入口为 `kubengine app task-worker`；原 `kubengine app image-worker` 及 `kubengine-image-worker.service` 保持兼容。两者运行同一个 worker，同时处理应用和镜像任务。CLI 部署继续使用自己的检查点，不进入 HTTP 任务表。
4. 同步发布 dashboard 构建产物，确保部署请求带上幂等键。服务端保留无键兼容，但无法替旧客户端识别两个独立请求是否为同一次提交。

租约、文件锁与 SQLite 协调范围仍为同一安装目录内的本机进程。正在执行的外部命令不能因租约变化而事务回滚；恢复策略是在持久化意图约束下重复检查外部状态，不承诺跨数据库与 Helm 的严格“只执行一次”。
