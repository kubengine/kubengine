# KubeEngine 项目设计审查

审查日期：2026-09-28。对象：当前工作区源码、测试、配置加载和发布脚本。

修复进展：安全边界与资源管理已实施一轮修复，详见[修复及升级说明](安全边界与资源管理修复-2026-09-28.md)。下文保留修复前的审查证据与编号，不代表每一项仍然存在。

项目已经具备离线部署、应用管理、镜像导入和日志追踪的完整功能骨架，但目前最需要投入的是安全边界、状态正确性和故障恢复。部分成功提示不能代表真实资源状态；配置变化和失败重试也不能保证安全重入。建议先修复这些问题，再扩大功能范围或提高并发。

本文是代码审查及隔离验证结果，不代表已完成真实集群验收。审查涉及 94 个 Python 源文件、约 26,202 行代码及相关脚本，重点追踪关键调用链；没有逐一运行所有应用 Chart。前端只有编译后的静态产物，没有可审查的前端源码和构建工程。

现有测试在临时配置、临时数据库和测试密钥下运行，结果为 **44 passed，6 warnings**。按仓库配置运行 mypy 得到 **190 项错误**，其中包含缺失类型存根、注解和第三方类型问题，不能把这个数字当作运行缺陷数量。另完成了隔离路由、临时 SQLite、模拟命令和故障路径验证。没有执行真实 SSH、部署、卸载或推送。

优先级：P1 表示应优先修复的安全、资源失管或关键能力故障；P2 表示应安排修复的正确性、恢复和可用性问题；优化项表示需要结合目标规模实施的设计改进。

## 1. 当前架构及主要矛盾

| 模块 | 当前职责 | 主要设计问题 |
| --- | --- | --- |
| `src/cli` | 管理入口、集群纳管、部署扩容、镜像构建 | 编排、状态、配置写入和命令执行集中；不同入口失败语义不一致 |
| `src/infra` | pyinfra 节点与组件操作 | 依赖外部完成标记，部分脚本本身不幂等；节点准备与组件安装混在一起 |
| `src/web` | HTTP、鉴权、上传、业务任务、WebSocket | 路由承担业务执行；自定义鉴权破坏参数注入；同步 I/O 阻塞事件循环 |
| `src/core/orm` | 数据模型、业务参数转换、任务恢复 | 持久化与业务编排混合；任务类型依赖 Python 模块路径 |
| `image_import_worker` | 带租约的镜像任务执行 | 已有持久化基础，但缺少过期执行者隔离和完整恢复语义 |
| `config` / SQLite / JSON 状态 | 配置、凭据、应用、任务与部署记录 | 多份状态缺少统一事务、版本和加载/写回规则 |
| `builder` | 镜像插件与制品构建 | 版本缓存、选项传递及资源生命周期存在遗漏 |
| 发布脚本 | wheel、Cython、RPM、systemd | 多套元数据、在线安装依赖、打包运行目录与错误吞掉 |

三处边界尤其值得调整：worker 反向导入 `web.api.artifacts`；核心客户端依赖 `web.utils.page`；应用部署任务在 Web 进程执行、恢复却由 image-worker 启动。它们让业务执行依赖 HTTP 层的初始化与模块命名。

## 2. 优先修复的问题

### R01 · P1 · 未鉴权静态路由可越界读取文件

位置：[web/main.py:303](/opt/kubengine/src/web/main.py:303)。

SPA fallback 将 URL 的 `full_path` 直接与静态目录拼接，仅检查存在后返回 `FileResponse`，没有限制解析后的路径必须位于静态目录中。带编码的上级目录路径能选中目录外文件；服务默认以 root 运行时，影响范围包括进程可读的配置、数据库和密钥。认证模块又读取 CA 私钥作为 JWT 签名材料，文件泄露会进一步影响认证。

隔离验证：ASGI 请求选中了临时静态目录外文件；该请求验证使用响应替身检查目标路径，另直接调用原函数确认真实 `FileResponse` 指向临时标记文件，没有读取真实敏感文件。

建议：静态资源统一交给 `StaticFiles`，SPA fallback 只返回固定 `index.html`。验收应覆盖编码路径、绝对路径、符号链接和不存在文件，目录外文件不得返回。

### R02 · P1 · Chart 上传文件名可控制宿主机路径及 Shell 参数

位置：[artifacts.py:650](/opt/kubengine/src/web/api/artifacts.py:650)、[artifacts.py:667](/opt/kubengine/src/web/api/artifacts.py:667)、[command.py:281](/opt/kubengine/src/core/command.py:281)。

已认证上传只检查后缀和大小，随后用客户端文件名构造 `/tmp` 下路径，并直接拼入 `helm push`。绝对路径会覆盖前面的目录；路径分隔符、Shell 元字符和同名并发上传均未隔离。后续清理还会删除这个路径。

隔离验证确认可覆盖并删除预置的临时 `.tgz` 文件，且 Shell 替换语法会原样进入命令字符串；验证没有执行该命令。

建议：服务端生成独占的随机临时路径，原文件名仅作展示信息；命令执行支持参数数组和 `shell=False`。应用部署等其他命令拼接入口也应按同一标准收敛。验收包括恶意文件名、空格、并发同名和异常清理。

### R03 · P1 · 普通日志记录了仓库认证凭据

位置：[base_builder.py:704](/opt/kubengine/src/builder/image/base_builder.py:704)、[artifacts.py:869](/opt/kubengine/src/web/api/artifacts.py:869)、[command.py:330](/opt/kubengine/src/core/command.py:330)。

镜像推送将用户名和密码放入命令参数，执行器在 INFO 级别记录完整 `command_end.command`；异常分支也记录原命令。关闭 `log_output` 不能阻止这类日志。用虚拟凭据执行无副作用命令已确认：渲染后的日志和结构化字段均保留该凭据。

建议：分离执行参数与日志描述，在进入 LogRecord 前统一脱敏；优先使用权限受限的认证文件或工具支持的安全输入方式。验收同时检查普通输出、结构化字段、异常堆栈及命令失败信息。

### R04 · P1 · 鉴权装饰器使登出和 SSH 接口无法正常调用

位置：[auth.py:374](/opt/kubengine/src/web/utils/auth.py:374)、[auth.py:431](/opt/kubengine/src/web/utils/auth.py:431)、[auth_routes.py:47](/opt/kubengine/src/web/api/auth_routes.py:47)、[ssh.py:70](/opt/kubengine/src/web/api/ssh.py:70)。

`@wraps` 保留了 `current_user: User` 参数，FastAPI 把它识别为请求体；装饰器又把真实认证用户作为位置参数传入，但没有移除框架提供的同名参数。隔离 ASGI 验证中，模拟认证依赖返回合法用户后，不提供 User body 返回 422，补齐 body 后因重复参数返回 500。影响登出、统一鉴权示例和四个 SSH 接口。

建议：改用 `Depends(get_current_user)`，把续签和响应封装与身份注入分开。通过真实路由测试验证：客户端只提供业务参数和认证头即可调用，不应提交内部 User 对象。

### R05 · P2 · AK/SK 路径不可用，签名协议也未闭环

位置：[auth.py:252](/opt/kubengine/src/web/utils/auth.py:252)、[auth.py:280](/opt/kubengine/src/web/utils/auth.py:280)、[auth.py:198](/opt/kubengine/src/web/utils/auth.py:198)。

仅提供 AK/SK 请求头会先被 Bearer 格式检查拒绝；增加无效 Bearer 后，AK/SK 分支构造 User 时缺少 username，抛出 ValidationError。这两种故障均已隔离复现。

此外，签名验证读取的密钥与 CLI 保存的 `sk_hash` 不匹配，并有固定默认密钥；签名不包含请求方法、路径、正文，nonce 也没有去重。后者是修复分支前必须解决的协议问题，本次没有把它判定为已成功利用的认证绕过。

建议：明确认证方式选择，移除默认密钥，设计可验证的密钥存储和规范化请求签名，加入时间窗口与 nonce 去重。只修 Bearer 判断和 username 不足以交付该功能。

### R06 · P1 · 配置变化及失败续跑可能重做已有集群初始化

位置：[cli/k8s.py:565](/opt/kubengine/src/cli/k8s.py:565)、[install_kubernetes.py:42](/opt/kubengine/src/infra/install_kubernetes.py:42)、[install_kubernetes.py:102](/opt/kubengine/src/infra/install_kubernetes.py:102)、[kubernetes_join_node.py:27](/opt/kubengine/src/infra/kubernetes_join_node.py:27)。

配置哈希变化会清空所有完成状态并重跑全部组件；Kubernetes 脚本会停止 kubelet，再无条件执行 `kubeadm init --ignore-preflight-errors=all`。扩容修改 worker 列表后再 deploy 就能进入此分支。多节点部分成功后重试，也会对已经 join 的节点重放 join；多个 Helm 安装脚本使用裸 `helm install`。

影响是正常节点被停止、重复初始化或重复安装失败，续跑可能扩大原故障。本次未对真实集群执行这些操作，不能断言必然造成数据损坏。

建议：分离首次初始化、配置协调、扩容、升级；按节点和步骤记录状态，并查询远端实际状态做幂等判断。普通配置变更不得自动触发 init。验收必须包含已部署集群重跑、部分节点成功后重试、扩容后再 deploy。

### R07 · P1 · 离线扩容缺少新节点完整运行依赖和就绪验收

位置：[cli/k8s.py:1202](/opt/kubengine/src/cli/k8s.py:1202)、[cli/k8s.py:1257](/opt/kubengine/src/cli/k8s.py:1257)；对照 [install_calico.py:13](/opt/kubengine/src/infra/install_calico.py:13)、[install_longhorn.py:21](/opt/kubengine/src/infra/install_longhorn.py:21)。

scale 只执行 Chrony、containerd、CNI 二进制、证书、Kubernetes 核心和 join，没有复用 Calico/Longhorn 等节点侧镜像准备，也没有安装 Longhorn 的 open-iscsi 等前置依赖。全新离线节点没有这些缓存且仓库不可用时，可以 join 后卡在网络或存储不可用状态，CLI 仍宣告扩容成功。

建议：提取 deploy/scale 共用的节点准备流程，按已启用组件生成镜像及系统依赖清单；成功条件包含 Node Ready、CNI 和存储状态。验收使用无镜像缓存、无互联网的新节点。

### R08 · P1 · SSH 互信覆盖已有授权，可能撤销运维登录能力

位置：[core/ssh.py:814](/opt/kubengine/src/core/ssh.py:814)。

实现将本次 hosts 的公钥集合写成整个 `authorized_keys`，没有保留原有运维、自动化和救援密钥。部分节点可达时同样可能删掉未参与本次操作的授权；现有 SSH 会话仍然存活，容易掩盖新连接已经被锁出的事实。

建议：仅维护本工具拥有的条目或独立授权文件，保留外部条目；先备份、追加和验证。验收在包含旧密钥的机器上执行互信，确认原有授权仍可建立新连接。

### R09 · P1 · SSH 默认不校验目标主机身份

位置：[core/ssh.py:116](/opt/kubengine/src/core/ssh.py:116)。

连接默认传入 `known_hosts=None`，密码初始化阶段尤其敏感。能够劫持目标地址或链路的攻击者可以冒充 SSH 服务端；后续扫描并写入 known_hosts 不能弥补首次连接的身份未验证。

建议：默认严格校验主机密钥，首次纳管采用预分发指纹或明确的信任建立步骤；主机密钥变化应失败并报告原因。验收覆盖错误指纹和更换密钥场景。

### R10 · P1 · 控制面高可用未覆盖 apiserver 故障

位置：[install_keepalived.py:75](/opt/kubengine/src/infra/install_keepalived.py:75)。

当前配置只有 VRRP，没有跟踪 API 服务健康。当持有 VIP 的节点上 apiserver 不可用，但主机、网络和 keepalived 正常时，VIP 不会因此迁走，即使其他控制面健康也无法恢复统一入口。

建议：增加本机 API readiness 检查并降权或进入 FAULT，或使用能检查各 API 后端的负载均衡层。验收既测试整机故障，也单独停止 API 服务。另需修复网卡自动检测使用部署机本地结果的问题（脚本第 44 行），支持逐节点接口信息。

### R11 · P1 · 应用删除重试会丢失管理记录，任务状态及恢复也不可信

位置：[web/api/app.py:126](/opt/kubengine/src/web/api/app.py:126)、[web/api/app.py:142](/opt/kubengine/src/web/api/app.py:142)、[web/api/app.py:174](/opt/kubengine/src/web/api/app.py:174)、[web/api/app.py:236](/opt/kubengine/src/web/api/app.py:236)、[orm/task.py:90](/opt/kubengine/src/core/orm/task.py:90)。

这里有三个需要一起修复的问题：

- 部署、卸载异常被吞掉，finally 无条件把任务记为 success。
- 卸载失败把应用实例置为 anomaly；再次删除时会跳过 Helm 卸载，直接删除数据库记录，留下实际资源失管。
- 部署和删除都保存 `api.app.deploy_app`，与恢复白名单的 `web.api.*` 不匹配；删除还被错误登记为部署操作，清理函数没有正确注册。

隔离验证确认：第一次卸载失败后任务显示 success；第二次调用没有新增 Helm 执行，却删除了记录。两个任务入口持久化的函数路径都不能通过恢复白名单。

建议：使用稳定的任务类型注册表，由一个执行器管理终态；清理失败保留记录并允许重试，确认资源不存在后再删除。创建应用记录和待执行任务应同事务提交，业务执行迁入持久化 worker，按外部实际状态恢复。验收覆盖 API/worker 重启和卸载中断。

### R12 · P2 · 镜像租约丢失后，旧 worker 仍能改写新任务状态

位置：[image_import_worker.py:55](/opt/kubengine/src/core/image_import_worker.py:55)、[orm/image_import.py:264](/opt/kubengine/src/core/orm/image_import.py:264)、[artifacts.py:732](/opt/kubengine/src/web/api/artifacts.py:732)。

续租失败只退出心跳线程，执行线程继续运行；任务和明细更新仅按 task_id，没有检查 owner 或执行次数。旧执行者停顿后恢复，可以把新 owner 的任务写成 success 并清掉 owner。文件锁能串行化 containerd 操作，但不能解决任务状态所有权问题。

临时 SQLite 复现确认：旧 owner 续租返回 False 后仍能覆盖新 owner 的终态。

建议：领取时分配 attempt/fencing token，每次进度与终态写入都做所有权条件更新；失去租约停止后续步骤，外部副作用保持幂等。验收让旧执行者在新执行者接管后恢复，所有过期写入必须被拒绝。

### R13 · P2 · 镜像失败项重试中断后，processing 项会被永久遗漏

位置：[artifacts.py:754](/opt/kubengine/src/web/api/artifacts.py:754)、[artifacts.py:814](/opt/kubengine/src/web/api/artifacts.py:814)、[artifacts.py:873](/opt/kubengine/src/web/api/artifacts.py:873)。

用户重试只选择 failed 项，推送前先将其改为 processing。若此时进程退出，下一 worker 继承 `retry_failed=True`，不会选择遗留 processing 项。隔离验证结果为没有执行 push，任务 failed、明细仍 processing、成功和失败数量均为零。

建议：区分用户发起重试与恢复中断执行；恢复处理所有未成功项，并归一化中断状态。验收在推送开始后模拟退出并重新领取。

### R14 · P2 · Helm 参数转换改变用户输入的类型和值

位置：[orm/cluster.py:167](/opt/kubengine/src/core/orm/cluster.py:167)、[misc/properties.py:174](/opt/kubengine/src/core/misc/properties.py:174)。

已按字段定义转换的标量又拼成 `key=value` 后重新猜测类型。已复现：声明为字符串的 `001234` 变成整数、`false` 变成布尔、`null` 变成空值，包含 `=` 的合法值直接报错。`bool("false")` 还会被解释为 True。密码、编码和连接参数会受到影响。

建议：直接把有类型的值赋给拆分后的字典键路径，不经过字符串中转；严格按字段 schema 校验。验收覆盖前导零、布尔字样、等号、空白、数组和带点的键名。

### R15 · P2 · 没有 Pod 被当成应用健康

位置：[helm_resource_check.py:154](/opt/kubengine/src/core/http_api_client/helm_resource_check.py:154)、[helm_resource_check.py:178](/opt/kubengine/src/core/http_api_client/helm_resource_check.py:178)。

初始结果为 success，查询不到 Pod 时直接 break，最终返回 `status=True, details=[]`。控制器尚未创建 Pod、标签选择不匹配或资源没有正确生成时，都可能过早判健康；该返回值直接参与应用状态更新。已用模拟空 Pod 列表复现。

建议：依据 Chart 预期工作负载判断是否需要 Pod，检查 Deployment/StatefulSet 等控制器的 observed generation 和期望副本数；没有预期 Pod 时继续等待或超时失败。合法的无 Pod Chart 应使用明确的独立规则。

### R16 · P2 · WebSocket 失败广播会死锁，且状态不跨进程

位置：[misc/websocket.py:30](/opt/kubengine/src/core/misc/websocket.py:30)、[cli/app.py:103](/opt/kubengine/src/cli/app.py:103)。

广播持有 `asyncio.Lock` 时，发送失败后调用 disconnect，再次获取同一把锁，导致死锁。模拟连接抛出异常后，广播在超时内无法返回，已复现。持锁顺序发送也会被慢客户端拖住。

另外连接表仅存在于当前进程；默认两个 Web worker，独立 image-worker 的恢复任务也可能发事件，单进程广播不能覆盖其他进程的连接。业务线程里 `asyncio.run` 也没有可靠地把发送安排回连接所属事件循环。

建议：锁内只复制或修改连接集合，锁外并发且有超时地发送；用共享事件表加轮询或消息通道传递跨进程事件，由各 Web worker 在自身循环发送。验收包含断连、慢客户端、多 worker 及独立 worker 完成任务。

### R17 · P2 · 同步无超时 I/O 会阻塞整个 Web worker

位置：[web/api/k8s.py:38](/opt/kubengine/src/web/api/k8s.py:38)、[web/api/k8s.py:96](/opt/kubengine/src/web/api/k8s.py:96)、[harbor_client.py:78](/opt/kubengine/src/core/http_api_client/harbor_client.py:78)、[longhorn_client.py:53](/opt/kubengine/src/core/http_api_client/longhorn_client.py:53)。

多个 async 路由直接调用同步 requests、Kubernetes 客户端或命令执行；多数 requests 调用没有 timeout。把同步调用放进 async 函数或 asyncio.gather 并不能让它并行。隔离验证中，模拟 150ms 上游等待使 10ms 定时器延迟到约 151ms。上游持续不返回会占住所属 worker，默认两个 worker 的容量很容易耗尽。

建议：所有客户端统一连接/读取超时；采用异步客户端，或显式将同步调用卸载到受控线程池。长命令进入任务队列。先测上游慢响应时的健康检查延迟和并发吞吐，再决定增加 worker。

### R18 · P2 · 更新 MetalLB 地址池执行成功也会返回失败

位置：[k8s_client.py:326](/opt/kubengine/src/core/http_api_client/k8s_client.py:326)。

`execute_command` 返回 CommandResult，但调用方使用字典 `.get()`，必然抛 AttributeError。此时 manifest 已写入，kubectl apply 也已经执行，响应却返回 500，客户端可能据此重复提交。

建议：统一 CommandResult 契约；先验证变更，正确检查退出码，并明确本地文件写入与远端应用失败的处理规则。验收同时覆盖成功、kubectl 失败以及文件写入失败。

### R19 · P2 · 配置写回、凭据轮换和多进程会话失效不一致

位置：[config_dict.py:255](/opt/kubengine/src/core/config/config_dict.py:255)、[cli/app.py:222](/opt/kubengine/src/cli/app.py:222)、[cli/cluster.py:469](/opt/kubengine/src/cli/cluster.py:469)、[web/utils/auth.py:39](/opt/kubengine/src/web/utils/auth.py:39)、[auth_routes.py:56](/opt/kubengine/src/web/api/auth_routes.py:56)。

读取支持 KUBEENGINE_CONFIG，写入却固定到 ROOT_DIR/config/application.yaml。使用其他配置文件时，改密或纳管提示成功，下次启动仍读取旧文件。即使用默认路径，运行中 Web 进程里的 USERS 也是导入时副本，不会随 CLI 改密更新。token 黑名单同样是进程内字典：修复登出接口后，仍不能保证另一 worker 或重启后拒绝旧 token。

仓库配置也存在分叉：[harbor_client.py:41](/opt/kubengine/src/core/http_api_client/harbor_client.py:41) 和 Chart 上传使用固定默认凭据，镜像推送则读取 Application.REGISTRY，改密后不同操作会出现不同结果。

建议：保存并写回实际配置来源，配置写入原子化；凭据由统一服务加载和轮换，采用共享撤销状态或用户会话版本。JWT 密钥与 TLS CA 私钥分离。验收包括自定义配置路径、轮换后全部 worker、重启后旧 token、非默认 Harbor 凭据。

### R20 · P1 · RPM 发布与离线运行目标冲突，并吞掉初始化失败

位置：[kubengine.spec:191](/opt/kubengine/kubengine.spec:191)、[kubengine.spec:217](/opt/kubengine/kubengine.spec:217)。

RPM 的 post-install 在线 pip 安装依赖，同时丢弃错误并继续报告安装完成；在无预装依赖的离线目标机上无法形成可启动的交付物。数据库初始化调用 `python -m cli.app init-data`，缺少实际 CLI 的 `app` 子命令层；检查的数据库路径也不是 ORM 使用的 config/sqlite.db，错误再次被吞掉。

建议：构建阶段准备锁定版本、带校验的离线 wheelhouse 或隔离运行环境，安装阶段不依赖互联网。初始化使用真实 CLI 入口和统一数据路径，失败应返回可诊断错误。验收在干净、断网的目标系统安装 RPM，执行 CLI 和服务启动冒烟测试。

### R21 · P1 · RPM 源码打包会夹带运行目录中的私钥和配置

位置：[scripts/build_rpm.sh:112](/opt/kubengine/scripts/build_rpm.sh:112)；另见 [MANIFEST.in:9](/opt/kubengine/MANIFEST.in:9)。

RPM 源码包从当前目录整体 rsync，排除日志、数据库等，但没有排除 config/certs、私钥或 tmp；该操作不自动遵循 .gitignore。在已运行过项目的目录构建，会把这些文件复制进源码 tarball，进而随源码包/SRPM 分发。使用真实排除规则和临时假文件树已确认：虚构私钥、token、运行配置和部署状态都进入归档。这里确认的是源码包/SRPM，不能据此断言私钥也进入二进制 RPM。pip sdist 的 config 通配规则也会收集运行中生成的 YAML/JSON/TOML 配置，而不只模板。

建议：发布输入来自干净检出和明确文件白名单，配置模板与运行目录分离。验收使用虚构私钥、虚构运行配置和临时文件，检查 tarball、sdist、wheel、RPM/SRPM 的成员列表中没有这些标记。

## 4. 建议的设计优化

### 4.1 统一任务模型，保留现有单体部署方式

当前阶段可以继续使用模块化单体与独立 worker，不需要先拆成多个服务。优先让 HTTP/CLI 只负责校验和提交意图，业务服务负责编排，执行适配器负责 Helm、SSH、containerd，存储层负责事务。

应用部署、删除和镜像导入统一遵循 pending → running → succeeded/failed/cancelled；用任务类型、资源 ID、attempt、owner、租约、错误和幂等键表达执行。任务记录成功和目标资源健康是两个不同维度，不能互相代替。集群/应用状态以实际资源检查为依据，事件通知失败不应改变部署结果。

### 4.2 把部署能力拆成可复用的操作阶段

明确节点准备、控制面初始化、加入节点、组件协调、升级和删除的前置条件与后置条件。节点准备由 deploy/scale 共用；每个步骤能回答“已满足什么、还缺什么、重试会做什么”。固定 sleep 改为带 deadline 的条件等待，配置更新先生成可审查的变更计划。部署与扩容之间增加互斥，避免同时改共享文件和节点。

不要把“执行过脚本”当成“目标仍满足要求”，也不要把配置指纹变化当成重置整个系统的授权。

### 4.3 SQLite 可以继续使用，但需要明确运行边界

先完善 WAL、busy timeout、外键、短事务、版本化迁移与备份恢复，再根据多机部署和实际写入压力决定是否换数据库。`create_all` 加局部 ALTER 不足以承担长期升级。应用模板与任务应避免跨多个提交形成半成品；`init-data --force` 的清空与重建也应具备整体事务或暂存切换。

列表查询按 DTO 所需字段加载，避免逐条懒加载应用字段、把镜像任务所有明细都塞进分页列表。以真实列表大小测查询次数和响应体积后优化。

### 4.4 镜像并发必须与资源隔离一起设计

目前导入任务共享 containerd 的 apps namespace，并用文件锁覆盖导入、推送和清理；简单增大 worker 并发不会相应提高吞吐。若需要并行，优先采用每任务独立 namespace/资源所有权，清理仅删除该任务拥有的资源，保留全局并发和磁盘配额。

为 uploading 超时、原始上传文件、失败任务、任务明细和构建容器制定保留与清理规则，避免长期运行耗尽磁盘。健康检查应区分进程存活、队列可领取和上游依赖可用。

### 4.5 配置、业务模型与凭据分开管理

使用强类型配置集中校验，缺字段立即给出明确错误；避免属性缺失静默返回 None、导入时注入和多份长期缓存。保留实际来源、schema 版本及变更记录。CA 生成/轮换应成为显式操作，不在普通模块导入时触发；当前 create_cert 指纹变化会重新生成整条链，需要有独立的分发与切换流程。

ORM 中的 Cluster 实际表示一个应用的 Helm 实例，建议逐步命名为 AppDeployment/HelmRelease，避免与 Kubernetes 集群混淆。请求、数据库实体、响应和执行参数使用各自模型，减少 Optional[Any] 式宽泛数据进入命令层。

### 4.6 收敛构建发布和测试入口

以 pyproject.toml 为主要元数据来源，统一 setup.py、setup_install.py、RPM 与文档中的依赖和版本；增加离线可复现依赖清单。Cython 是否启用应是明确构建选项，而不是由构建机碰巧安装了什么决定；扩展列表目前递归收集产生重复项，需要去重。

本次在临时项目副本、禁用可选 Cython 的条件下构建纯 Python wheel 成功，抽查 ORM、builder、infra 等关键模块存在，**没有将现代 wheel 判定为缺包**。该结果不替代 Cython/RPM 安装测试。

前端应补充源码仓库关联、构建命令、依赖锁及与后端版本的对应关系；仅保留压缩 JS 不能形成可维护、可复现的交付链。仓库内未见 CI 配置，建议将关键检查固化到实际使用的 CI 平台。
