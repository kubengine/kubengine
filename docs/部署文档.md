# Kubengine 部署文档

## 一、前期准备

### 1.1 上传并解压安装包

将 `kubengine.tar.gz` 上传到目标服务器，并解压缩：

```bash
scp kubengine.tar.gz root@192.168.1.100:/opt/
ssh root@192.168.1.100
cd /opt/
tar -zxf kubengine.tar.gz
```

### 1.2 激活虚拟环境

```bash
cd /opt/kubengine/
source env/bin/activate
```

> **说明**：后续所有 `kubengine` 与 `kubengine-k8s` 命令均需在虚拟环境中执行。

## 二、集群配置

### 2.1 配置集群信息

```bash
kubengine cluster config \
  --hosts 172.31.96.11,172.31.96.10,172.31.96.1,172.31.96.12,172.31.96.14,172.31.96.13 \
  --hostname-map 172.31.96.11:master01,172.31.96.10:master02,172.31.96.1:master03,172.31.96.12:node01,172.31.96.14:node02,172.31.96.13:node03 \
  --username root --password Avic@123
```

### 2.2 查看集群配置

```bash
kubengine cluster show
```

### 2.3 关闭防火墙

```bash
kubengine cluster disable-firewalld
```

### 2.4 调整 sshd（离线文件分发与节点免密都用它）

worker / 附加 master 的离线文件是从 master 的 sshd 上以 SFTP 方式拉的；
`kubengine cluster config` 配置节点免密时，每个节点也会同时收到来自其它所有
节点的连接。所以建议**所有节点**都落一遍下面这份配置，写入
`/etc/ssh/sshd_config.d/kubengine.conf` 后 `systemctl reload sshd`：

```
ClientAliveInterval 30
ClientAliveCountMax 3
MaxStartups 100:30:200
MaxSessions 100
```

改完可用 `sshd -T | grep -Ei 'clientalive|maxstartups|maxsessions'` 确认生效。

## 三、调整部署配置

编辑配置文件：

```bash
vim /opt/kubengine/config/application.yaml
```

#### 单 master 配置示例

```yaml
kubernetes:
  master:
    ip: 按照要求填写        # master 节点 IP
    schedulable: false
  worker:
    ips: [按照要求填写]      # worker 节点 IP 列表
  cidr:
    pod: 10.96.0.0/16
    service: 10.97.0.0/16
  loadbalancer:
    ip-pools:
      - 按照虚拟交换机保留IP地址填写    # 示例: 172.31.57.30-172.31.57.40
```

#### 高可用（多 master）配置示例

```yaml
kubernetes:
  master:
    ip: 172.31.96.11                       # 第一个 master（必须）
    additional_ips:
      - 172.31.96.10                       # 附加 master02
      - 172.31.96.1                        # 附加 master03
    control-plane-endpoint: 172.31.96.100  # VIP（用于 apiserver HA）
    interface: ens31                       # 网卡名（可选，默认自动检测）
    schedulable: false
  worker:
    ips:
      - 172.31.96.12
      - 172.31.96.14
      - 172.31.96.13
  cidr:
    pod: 10.96.0.0/16
    service: 10.97.0.0/16
  loadbalancer:
    ip-pools:
      - 按照虚拟交换机保留IP地址填写    # 示例: 172.31.57.30-172.31.57.40
```

scp offline-deploy.tgz root@192.168.1.100:/root/

## 五、验证部署配置

```bash
# 显示当前配置
kubengine-k8s config --show
# 验证配置
kubengine-k8s config --validate
```

> **注意**：部署前务必执行 `--validate` 校验，确保配置无误。

## 六、准备数据盘（Longhorn）

在 worker 节点上格式化并挂载数据盘供 Longhorn 使用：

```bash
mkfs.ext4 /dev/vdc
umount /media/lanqing/vdc
mkdir /var/lib/longhorn/
mount /dev/vdc /var/lib/longhorn/
```

#### 批量配置 worker 节点（可选）

通过 `kubengine` 在多个 worker 节点批量执行，实现开机自动挂载：

```bash
# 写入开机挂载并生效
kubengine cluster exec \
  'echo "UUID=$(blkid -s UUID -o value /dev/vdc) /var/lib/longhorn ext4 defaults 0 0" >> /etc/fstab; mount -a' \
  --hosts 172.31.96.12,172.31.96.13,172.31.96.14

# 验证挂载结果
kubengine cluster exec 'lsblk -f | grep longhorn' \
  --hosts 172.31.96.12,172.31.96.13,172.31.96.14
```

## 七、部署应用

```bash
kubengine-k8s deploy
```

> **日志路径**：部署详细过程日志位于 `/opt/kubengine/logs/k8s_cli.log`，可用于排查问题。

## 八、K8s 部署后初始化

等待所有 Pod 状态为 Running 后，依次执行以下初始化操作：

```bash
# 1. 初始化 Harbor 项目
kubengine-k8s init-harbor

# 2. 推送集群节点离线镜像到 Harbor（后续扩容节点可直接拉取）
kubengine-k8s push-images

# 3. 批量推送应用镜像与 Helm Charts 到 Harbor
kubengine-k8s sync-bitnami import-dir /root/offline-deploy/bitnami-bundles/

# 4. 初始化应用配置
kubengine app init-data
```

## 九、配置 API 服务（systemd 托管）

将 `kubengine app run` 配置为 systemd 服务，实现开机自启与自动恢复。

### 9.1 创建 service 文件

```bash
cat > /usr/lib/systemd/system/kubengine-api.service << 'EOF'
[Unit]
Description=KubeEngine API Service
After=network.target

[Service]
Type=simple
User=root
Environment="PATH=/usr/bin:/usr/local/bin"
ExecStart=/opt/kubengine/env/bin/kubengine app run --workers 2
ExecReload=/bin/kill -HUP $MAINPID
KillMode=control-group
TimeoutStopSec=10
KillSignal=SIGTERM
FinalKillSignal=SIGKILL
Restart=always
RestartSec=10
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
EOF

cat > /usr/lib/systemd/system/kubengine-image-worker.service << 'EOF'
[Unit]
Description=KubeEngine Durable Image Import Worker
After=network.target kubengine-api.service

[Service]
Type=simple
User=root
Environment="PATH=/usr/bin:/usr/local/bin"
ExecStart=/opt/kubengine/env/bin/kubengine app image-worker --concurrency 1
KillMode=control-group
TimeoutStopSec=30
Restart=always
RestartSec=5
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
EOF
```

### 9.2 启动并设置开机自启

```bash
systemctl daemon-reload
systemctl enable --now kubengine-api kubengine-image-worker
```

### 9.3 验证服务状态

```bash
# 查看服务状态
systemctl status kubengine-api
systemctl status kubengine-image-worker

# 查看实时日志
journalctl -u kubengine-api -f
journalctl -u kubengine-image-worker -f
```

服务默认监听 `0.0.0.0:8080`，通过浏览器访问 `http://<服务器IP>:8080` 即可打开管理界面。

## 十、平台版本升级与恢复

1. 核对实际 `KUBEENGINE_CONFIG`、`root_dir`、安装版本、服务进程和待执行任务。
   在隔离目录用运行库的一致快照预演新版本迁移、身份保留及权限，不向业务工作负载
   提交扩缩容或重启测试。旧任务缺少发起者、资源 UUID 或明确意图时先核实，不能
   直接补写当前身份来强行恢复。
2. 停止 API 和 worker，确认旧进程完全退出，不混跑新旧执行器。备份代码、静态资源、
   实际配置、数据库、JWT 签名密钥、YAML 历史加密密钥及 CLI 部署状态。目录限服务
   账号访问，敏感文件权限 0600；运行中备份 SQLite 使用 backup API，不只复制 WAL
   模式主文件。实际恢复备份到隔离目录并核验完整性后再更新。
3. 按文件清单更新代码和完整前端构建，移除过期静态产物，保留运行配置、密钥和虚拟
   环境。启动时会幂等创建或补齐表结构；首次身份迁移后数据库是唯一身份来源。
   缺少持久化会话 `sid` 的旧令牌失效，用户需要重新登录。
4. 启动两个服务，核对 worker 的新心跳、健康与依赖就绪状态，以及管理员登录、只读
   用户写入拒绝、跨命名空间访问拒绝。确认原身份、任务、资源版本及密钥均保留。

```bash
systemctl start kubengine-api kubengine-image-worker
systemctl is-active kubengine-api kubengine-image-worker
curl --fail http://127.0.0.1:8080/api/v1/health
curl --fail http://127.0.0.1:8080/api/v1/ready
```

回滚前停止所有写入者，限制普通用户流量并评估升级后的新增数据，不能不经核实恢复
整库。使用同一时点的数据库、密钥、配置与代码；旧版若不支持当前权限规则，不得直接
对普通用户开放。不要删除数据库或部署状态文件来恢复账号、绕过初始化或清除未知结果。
身份恢复细则见[用户权限与操作审计](用户权限与操作审计使用指南.md#迁移备份与恢复)，
后台任务与 Deployment 的核实规则分别见[API](API.md#任务恢复与清理)和
[Deployment 运维](Deployment运维.md)。
